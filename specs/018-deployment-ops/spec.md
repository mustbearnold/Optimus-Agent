# Spec-018: Deployment & ops — service-grade remote operation

## Purpose

Optimus today is a desktop-first product: the installers stage a
Tauri app plus CLI, and the only upgrade path is a reinstall script
(ADR-0043 chose "no auto-updater channel" at product-complete). There
is no supported way to run Optimus as a durable headless service on a
VPS, no systemd unit, no backup/restore commands (only a backup-path
inventory in `optimus doctor`), and no signed update channel. Hermes,
the parity target, runs as a service with an update channel and remote
operation.

This spec makes Optimus deployable and operable as a 24/7 service:
a headless install path with a dedicated service user, a hardened
systemd unit generated and managed by the CLI, online consistent
backup/restore built on the durability set the doctor already
inventories, and a signed update channel with staged atomic swap and
rollback — the exact mechanism ADR-0043's context names as the
acceptable alternative to the no-updater stance.

## Current state (Confirmed behaviour)

- `optimus doctor` (P18) inventories every durable DB's schema version,
  quarantine, and a fixed backup-path set: `backup_relative_paths()`
  in `apps/optimus-cli/src/doctor.rs` lists the process-local
  durability set and `doctor backup-list` prints it; the design is
  documented in `docs/architecture/state-and-memory.md`
  (Confirmed: code).
- The CLI command surface (`apps/optimus-cli/src/main.rs`) has no
  `backup`, `restore`, `service`, or `update` subcommand (Confirmed:
  command enum).
- Installers: `scripts/rebuild-install-relaunch.sh` (and `.ps1`)
  stage the Tauri app + CLI; the SOTA scorecard records "Release
  updater: no in-app signed auto-update channel (ADR-0043); reinstall
  script is the upgrade path" as a material partial (Confirmed:
  scorecard + ADR-0043).
- ADR-0043 (accepted 2026-07-25) states the P29 requirement: either a
  signed updater + rollback, or an explicit no-updater stance; the
  no-updater stance was chosen, with the reinstall script as the
  upgrade path (Confirmed: ADR-0043).
- The gateway delivery authority and cron store are durable local
  SQLite state owned by `crates/optimus-ops` (spec-007); a deployed
  service must keep that state consistent across restarts and
  backups (Confirmed: spec-007, `crates/optimus-ops`).
- There is no systemd unit, no service-management CLI, and no remote
  (VPS) install path in the installers (Confirmed: repo shape —
  no service/unit artifacts exist under `scripts/` or `apps/`).

## Requirements

### R1. Headless install with dedicated service user

- The Linux installer MUST support a headless mode that installs the
  CLI + runtime only (no desktop), under a dedicated service user with
  its own Optimus home, without a display server (MUST).
- Headless install MUST be non-interactive (flag-driven) so it runs in
  provisioning scripts and CI containers (MUST).
- The installed runtime MUST run with a dedicated Optimus home that is
  NOT the service user's login home: default `/var/lib/optimus` for a
  system unit (root install), and the user's XDG state dir for a user
  unit; the service MUST NOT require or touch the invoking user's home
  (MUST).
- A runbook (`docs/runbooks/vps-deployment.md`) MUST document the
  full remote deployment: service user creation, install, service
  enable, firewall/SSH basics as host-config pointers (not product
  requirements), and first-run verification (MUST).

### R2. systemd service lifecycle

- `optimus service install` MUST generate and install a systemd unit
  (system unit when run as root, user unit otherwise) whose ExecStart
  is `optimus gateway run` (the spec-017 supervisor), and
  `optimus service uninstall` MUST remove it; `optimus service
  install --print` MUST render the unit to stdout WITHOUT installing,
  so CI and operators can inspect the exact unit (MUST).
- The generated unit MUST be hardened: `NoNewPrivileges=yes`,
  `ProtectSystem=strict`, `ProtectHome=read-only`, `PrivateTmp=yes`,
  `Restart=on-failure`, `RestartSec` with capped backoff, an
  `Environment=` carrying the Optimus home, and `ReadWritePaths=`
  listing exactly the Optimus home (MUST).
- The unit's writable paths MUST be exactly the Optimus home (via
  `ReadWritePaths`) and nothing else — the supervisor writes every
  durable DB there, so the home MUST be a path the unit can actually
  write; the home MUST NOT be the service user's login home and MUST
  be covered by `ReadWritePaths` (system units default to
  `/var/lib/optimus`; user units default to the XDG state dir, whose
  default location under `/home` is still covered by the unit's
  `ReadWritePaths` nesting) (MUST).
- `optimus service status` MUST report unit state (active / failed /
  not-installed) plus the gateway supervisor's per-adapter state
  (MUST; forwards to spec-017's status surface).
- The generated unit MUST be reproducible: identical inputs produce
  identical unit text (deterministic generation, no timestamps)
  (MUST).
- CI MUST validate unit generation without a live systemd: a gate test
  renders the unit into a scratch dir and asserts the hardening flags
  (`NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`,
  `Restart=on-failure`, `ReadWritePaths` containing the home from
  `Environment=`), `ExecStart=optimus gateway run`, and byte-identical
  re-render; a live `systemctl` smoke test is manual/flagged (MUST).

### R3. Online consistent backup and restore

- `optimus backup` MUST produce a consistent snapshot of every DB in
  the doctor inventory (e.g., sessions, memory, ops/gateway, cron,
  work graph — whatever `backup_relative_paths()` enumerates, which
  also includes skills, execution, and workflow/ledger DBs) using the
  SQLite online backup API (WAL-safe, no downtime),
  plus the artifacts dir (as inventoried by
  `backup_relative_paths()`) and the config files carrying no secrets
  (MUST).
- The SQLite online backup API requires enabling the rusqlite
  `backup` cargo feature (the root manifest currently enables only
  `bundled`); that dependency delta lands in the same change (MUST).
- The snapshot MUST be written as a versioned archive under a
  configured backup dir with a SHA-256 manifest listing every entry and
  the product version; secrets-bearing config files MUST be excluded
  from the archive (MUST).
- `optimus backup` MUST be safe to run while the gateway is actively
  delivering messages (consistent, not merely copied) (MUST).
- `optimus restore --verify` MUST verify every hash in the manifest
  before writing anything, and MUST refuse to restore over a live
  Optimus home (named diagnostic `restore_target_live`) unless
  `--force-offline` is passed (MUST).
- Restore MUST drop/clear `-wal`/`-shm` sidecar files before writing
  the snapshot, so stale WAL frames can never replay over a fresh
  self-contained snapshot (MUST).
- Backup cadence MAY be wired into the existing cron store (spec-007)
  as a scheduled job (MAY).
- The existing `doctor backup-list` inventory MUST remain the single
  source of truth for which paths backup covers; adding a path to
  backup means adding it to `backup_relative_paths()` (MUST).

### R4. Signed update channel with staged swap and rollback

- `optimus update` MUST implement the signed updater + rollback path
  ADR-0043 names: a manifest (version, artifact SHA-256, ed25519
  signature) is fetched from a configured channel URL; the signature
  MUST verify against a public key pinned in the binary at compile time
  (MUST).
- A manifest with an invalid signature or a hash mismatch MUST be
  refused with the named diagnostic `update_signature_invalid` /
  `update_hash_mismatch`, and MUST NOT touch the installed binary
  (MUST).
- The update MUST be staged (download to a staging dir, verify), then
  atomically swapped (rename dance), then the new binary MUST pass a
  startup probe (`--version` + a bounded `doctor` health call); if the
  probe fails, the previous binary MUST be restored automatically and
  the failure reported with a named diagnostic `update_rollback`
  (MUST).
- `optimus update --rollback` MUST restore the previous version
  explicitly on operator request (MUST).
- `optimus update --dry-run` MUST report availability without writing
  (MUST).
- The new ADR superseding ADR-0043's no-updater stance MUST be written
  in the same change that lands the update channel, marking ADR-0043
  `status: historical` with a supersession note (MUST; repo ADR law).
- The same change MUST update the scorecard's `release.updater`
  partial row (`docs/architecture/sota-scorecard.md`) and any ledger
  rows tied to the no-updater stance, so no stale doc still claims
  the reinstall script is the upgrade path (MUST).
- The update channel URL and its public key fingerprint MUST be
  printed by `optimus doctor` (see R5) (MUST).

### R5. Service health and observability

- `optimus doctor` MUST gain a service section: systemd unit state,
  update-channel status (URL, key fingerprint, last check, version
  available), free disk space on the Optimus home volume, and a fast
  DB integrity check (MUST).
- `doctor` MUST exit 1 when any named issue is present (existing
  contract) and the service section's issues MUST be named
  diagnostics, not prose (MUST).
- The service MUST log to journald by default (unit owns stdout/stderr
  forwarding); log rotation is journald's (MUST).
- Every durable operation (`backup`, `restore`, `update`,
  `update --rollback`) MUST emit ordered event rows in the
  observability plane (AGENTS.md law 11) with the outcome recorded
  (MUST).

### R6. Secrets discipline for the deployed service

- Service tokens (adapter tokens from spec-017, provider keys) MUST
  live in the service user's config home with mode 0600; the config
  home MUST be mode 0700 (MUST).
- `optimus doctor` MUST flag a config file with mode 0644 or wider as
  the named issue `config_permissions_too_open` (exit 1) instead of
  passing silently (MUST; the doctor's existing issue contract).

## Acceptance criteria

- [ ] A1. Given a headless install flag set, when the installer runs
  as a non-root user in a scratch home (CI container), then a CLI-only
  install lands under that home with no display dependency, and
  `optimus --version` runs (R1).
- [ ] A2. Given `optimus service install`, when the unit is rendered
  into a scratch dir (CI, no live systemd), then the gate test asserts
  the hardening flags (`NoNewPrivileges`, `ProtectSystem=strict`,
  `PrivateTmp`, `Restart=on-failure`), `ExecStart=optimus gateway
  run`, and byte-identical re-render (R2).
- [ ] A3. Given a running gateway with queued activity, when
  `optimus backup` runs, then the archive + hash manifest is produced
  and `optimus restore --verify` into a scratch home yields
  byte-identical DBs (hash-compared) (R3).
- [ ] A4. Given a valid signed manifest, when `optimus update
  --dry-run` runs, then it reports the available version without
  writing anything (R4).
- [ ] A5. Given a tampered manifest, when `optimus update` runs, then
  it is refused with `update_signature_invalid` and no binary is
  touched (R4).
- [ ] A6. Given a staged update whose new binary fails its startup
  probe, when the swap executes, then the previous binary is restored
  automatically and `update_rollback` is recorded (R4).
- [ ] A7. Given a deployed service with a 0644 config file, when
  `optimus doctor` runs, then it exits 1 with the named issue
  `config_permissions_too_open`; with 0600 the issue clears (R6).

## Out of scope

- Desktop auto-update UI: the CLI mechanism is v1; wiring it into the
  Tauri app is a follow-up (MAY be added later).
- Container images and orchestration (Kubernetes etc.); the systemd
  unit is the supported remote shape (MAY add containers later).
- Multi-node HA / clustering.
- Windows and macOS service units (Linux systemd only in v1).
- SSH, firewall, and Tailscale configuration (host-level concerns;
  runbook pointers only per R1).

## Open questions

- Update channel hosting: GitHub Releases vs self-hosted static
  hosting — to be settled by the supersession ADR in R4.
- Whether `restore` should also restore the artifact store or only
  DBs + manifest in v1 — default: DBs + manifest; artifacts restored
  on demand.
- Systemd user units on hosts without lingering user sessions
  (`loginctl enable-linger`) — document in the runbook or require
  system units on VPS; default: system unit on VPS.
