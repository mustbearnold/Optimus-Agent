# ADR-0017: Repository-local Optimus Engineering Memory

- **Status:** Accepted
- **Date:** 2026-07-20

## Context

Optimus already has multiple Rust subsystems, durable stores, provider adapters,
security boundaries, tests, phase documents, and ADRs. Architecture knowledge is
spread across source, historical verification notes, and a future-oriented
blueprint. Coding agents can mistake planned behavior for implemented behavior,
duplicate ownership, or omit affected documentation after changing code.

The repository is currently not a Git checkout, so commit-based freshness alone
cannot identify the exact source state.

## Decision

Create a repository-local Engineering Memory with four layers:

1. concise repository-wide laws in `AGENTS.md`;
2. curated architecture, map, contract, decision, lesson, and plan documents
   with explicit claim-status labels and source/test coverage frontmatter;
3. focused repository skills for repeatable maintenance;
4. deterministic JSON indexes generated by
   `scripts/tools/engineering_memory.py` under `.engineering-memory/`.

Engineering Memory is development knowledge only. It remains separate from
`optimus-memory`, sessions, runtime skills, gateway data, project knowledge, and
future production retrieval indexes.

Source and executable evidence outrank prose. Generated files are not manually
edited. Before generation, `check` reports affected/stale knowledge; after human
review, `generate` refreshes indexes and `validate` enforces structure. Until
Git exists, SHA-256 tree identities replace commit markers.

## Alternatives considered

### Put all guidance in `AGENTS.md`

Rejected because it would become a large, high-cost manual and obscure task-
specific procedures.

### Store Engineering Memory in `optimus-memory`

Rejected because runtime claims have different trust, retention, authorization,
and deployment boundaries from repository development knowledge.

### Generate all prose from an LLM

Rejected because deterministic repository facts should come from manifests and
source analysis, while human/agent interpretation must remain reviewable and
explicitly labeled.

### Restructure the repository to match a target template

Rejected because current Rust package boundaries are established and a large
rewrite would add risk without improving the memory foundation.

## Reasons

- Reduces repeated architectural rediscovery.
- Makes current, inferred, planned, and unresolved behavior distinguishable.
- Connects code changes to affected contracts, tests, and documents.
- Preserves historical ADRs instead of rewriting them.
- Works without Git while allowing commit identity later.
- Keeps routine small changes cheap through impact-based refresh.

## Consequences

- Substantial changes must run the Engineering Memory check/generate/validate
  sequence.
- Covered source changes intentionally mark related knowledge stale.
- Registry/index gaps remain visible rather than being filled speculatively.
- Existing documents can be migrated incrementally; they are not all rewritten
  in this decision.

## Risks

- Regex/source parsers can drift as Rust source shape changes; generation must
  fail closed and be regression-tested.
- Agents may regenerate without reviewing affected prose; the skill requires
  `check` before `generate` and validation cannot replace review.
- Tree hashes lack author/history semantics; use Git commit identity when the
  repository becomes a checkout.
- Generated indexes can create noise if they include build outputs; exclusions
  are explicit and tested.

## Evaluation evidence

Initial acceptance requires:

- deterministic generation twice with byte-identical results;
- validator success for generated integrity, links, frontmatter, unique IDs, and
  repository references;
- generator unit/integration tests;
- a clean staleness check immediately after generation;
- manual reconciliation of generated package/tool counts with Cargo and the
  canonical tool catalog.

## Conditions for reconsideration

Reconsider storage and generation boundaries if the repository becomes a
monorepo with independent release units, if Git returns, or if a typed compiler
API replaces source parsing. Do not merge Engineering Memory into runtime memory.
